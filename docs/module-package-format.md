## What a module is

A module is a **folder** with a `module.toml` at its top and its Luau code beside it, plus whatever images, sounds and data files it needs, in whatever subfolders it likes. In contrast to ReaHotkey (global `Images/`, `Sounds/` folders), **each module carries its own resources**, and every relative path it uses is resolved against its own folder (see [Paths](api/index.md#paths)).

```
my-game/                  the module's folder
├── module.toml           the manifest (required)
├── src/
│   ├── main.luau         the entry file (the default; `entry` changes it)
│   └── menus.luau        more code, loaded with host.include
├── images/
│   └── cursor.png        templates for image search — PNG only
└── data/
    └── pack.json         data, read with host.resource.read and host.json.decode
```

One module may define any number of overlays, triggers, hotkeys and polls from its entry file.

## Where modules are found

- **At start-up** the application loads every **direct** subfolder of `modules/` beside the application — beside the `.exe` on Windows, in the folder that holds the `.app` on macOS — that contains a readable `module.toml`. A folder whose `module.toml` is missing, unreadable or does not parse is skipped **without a message**, and so is a `.zip` file lying there. A folder nested one level deeper is not found.
- **From the command line**, `automation-platform <dir> [<dir> …]` runs the given folders instead of the installed ones. A path to a `.zip` is accepted there as well: the archive must have `module.toml` at its top, and it is unpacked into `<temp>/automation-platform-modules/<id>/<version>-<hash>/` and loaded from there.
- **From GitHub** — the module manager's Browse tab, or `automation-platform install owner/repo` — **one repository is one module**. Its `module.toml` must be at the repository root; the repository is downloaded and unpacked into `modules/<repository name>/` as a plain folder. A repository that holds several modules in subfolders cannot be installed this way.

So a pack of many modules — per-game modules generated by a tool, say — is installed locally: copy each module's folder directly under `modules/` beside the application, and they load at the next start (or run them from the command line while developing). A module copied in by hand gets no capability review.

A declared dependency is looked for among the folders beside the module that needs it, then in a `modules/` folder beside that.

## The manifest (`module.toml`)

TOML, because it is declarative and readable without running code.

```toml
id           = "com.example.my-game"          # required
name         = "My Game"                      # required
version      = "1.2.0"                        # required
entry        = "src/main.luau"                # optional; this is the default
dependencies = ["com.example.game-runtime >= 1.0, < 2"]
optional_dependencies = []
code_module  = false
supported_os = ["windows"]

[capabilities]
require = ["window", "screen", "ocr", "speech", "timer", "path", "resource"]

[screen]                                      # optional: which picture host.screen and host.ocr read
capture  = "duplication"                      # "standard" (default) | "duplication" (Windows only)
fallback = "standard"                         # with "duplication": "standard" (default) | "none"
```

These are **all the keys the host reads**:

| Key | Required | What the host does with it |
|---|---|---|
| `id` | yes | The module's identity: its settings, its enabled state, dependencies and `host.require` all go by it. |
| `name` | yes | Shown in the module manager and spoken in announcements. |
| `version` | yes | Shown in the manager and compared by the update check. It has to be semver (`1.2.0`) only when a dependent names a version range for it: then a version that is not semver fails the dependent's load. |
| `entry` | no | The file run when the module loads, relative to its folder. Default `src/main.luau`. |
| `dependencies` | no | Module ids, each optionally followed by a space and a semver range (`"com.x.y >= 1.2"`). Loaded before this module; a missing one, or one whose version does not satisfy the range, fails the load. A range that is not valid semver is logged and ignored. |
| `optional_dependencies` | no | The same grammar. Loaded only when present, never version-checked; [`host.tryRequire`](api/tryrequire.md) returns `nil` for one that is absent. |
| `code_module` | no | `true`: this module's code is also evaluated inside the VM of every module that depends on it, directly or through another `code_module`, so [`host.require`](api/require.md) returns its functions. It still runs in a VM of its own as well. Default `false`. |
| `supported_os` | no | See [below](#supported_os-and-why-omitting-it-is-the-safe-default). |
| `[capabilities] require` | no | The host namespaces the module may use. See [below](#capabilities). |
| `[screen]` | no | `capture` and `fallback`. See [below](#screen-and-why-it-is-declared-per-module). |
| `engine_api` | no | Read, and not used: nothing checks it against the running host. |
| `license` | no | Read, and not used. |

A missing `id`, `name` or `version` fails the load with `module.toml is not valid TOML`, followed by the parser's own message, which names the field (``missing field `name` ``). At start-up there is no message at all: a folder under `modules/` whose manifest lacks one is skipped (see [Where modules are found](#where-modules-are-found)).

**Any other key or table is ignored without a warning.** In particular the manifest has **no key for the window or process a module is meant for**: a `[window]` or `[match]` table, an `exe = …` or a `class = …`, is accepted and does nothing, and the module loads and runs on every system its `supported_os` allows. Window and process matching is Luau — [`host.window.find`](api/window.md#host-window-find), [`test`](api/window.md#host-window-test) and [`onTrigger`](api/window.md#host-window-ontrigger) with a [matcher](api/window.md#matchers), or an overlay binding. Nor is there a `[native]` table: a module cannot ship or load a native library.

### `[capabilities]` {#capabilities}

`require` lists the host namespaces the module's code may use, by the namespace's own name: `window`, `screen`, `ocr`, `element`, `input`, `keys`, `hotkey`, `gamepad`, `speech`, `sound`, `timer`, `settings`, `log`, `path`, `resource`, `arbiter`. The full rules are [in the API reference](api/index.md#capabilities); in short:

- There are no finer-grained names. `"window.read"` or `"screen.imagesearch"` unlock nothing.
- **Names are not checked.** A misspelt or invented one loads without a word, and the first use of the namespace it was meant for raises (`module 'com.example.my-game' used host.screen without declaring it — add "screen" …`).
- A module that only reads its own files still declares `path` and `resource`, and `log` if it logs.
- A `code_module` is judged by its own manifest wherever its code runs; what a dependent declares does not extend to it.
- The user sees the list once, before installing from GitHub. Nothing is granted or refused per capability, and a module copied into `modules/` by hand is not reviewed at all.

### `supported_os`, and why omitting it is the safe default

A module is already gated at runtime by its window matchers: one whose matcher has no block
for the current platform never matches, and the module sits there inert. So this field is not
what makes a module correct. It is what lets the application say something useful *before*
running it — warn before installing something that cannot work here, and not pay for loading
it.

What loading an inert module costs is small but not nothing: a VM, a matcher evaluated on
every focus change, any timer it starts, and any global shortcut it registers — which on the
wrong platform claims a key combination for something that can never happen, and shows the
user a conflict dialog about it.

Against that stands the fact that a manifest is a **claim**, and claims rot. Sforzando was
Windows-only one day and worked on both the next; a manifest still saying `["windows"]` would
have excluded a module that had just started working, and the reason would have been a line
in a file nobody reads. So:

- **Omitted means no claim, and no claim means every platform.** Every module written before
  this field existed goes on loading exactly as it did.
- A module that names platforms and not this one is **not loaded**, and says so in the log at
  every start, by name, with the reason.
- "Load modules not meant for this system" in the Application settings tab — or
  `AUTOMATION_PLATFORM_IGNORE_SUPPORTED_OS=1` for a launch without a window — loads it anyway,
  for the case where the manifest is simply behind the code.
- The install review says *"it can be installed, but it will not be loaded here"* rather than
  refusing. Refusing an install on the strength of one line in a text file is a stronger
  claim than that line can carry.

Names are `windows`, `macos`, `linux` — Rust's `std::env::consts::OS` values — matched
case-insensitively, because the file is written by hand and `"Windows"` is what a person
types.

### `[screen]`, and why it is declared per module

`[screen]` chooses the picture every `host.screen` and `host.ocr` read of the module sees. The
default, `standard`, is how every module has always read the screen. `duplication` reads it
through DXGI Desktop Duplication on Windows, for an application whose picture the standard
path reads frozen or black; `fallback = "none"` makes a read that duplication cannot answer
fail instead of returning the standard picture, for an application where that picture is
wrong rather than slow. The API reference has the details:
[Which picture a read sees](api/screen.md#which-picture-a-read-sees).

It is a declaration in the manifest, not a per-call option and not something the host
detects, for three reasons:

- **Whether the standard picture is wrong is a property of the target application**, and the
  module's author is the one who has tested that application. The person using the module —
  often blind — cannot see a frozen picture to report it.
- **One declaration covers every call.** A template cut from one picture is never matched
  against the other, which matters because the two can differ (HDR is converted for
  duplication, for one).
- **A frozen frame cannot be told from a still screen**, and a menu waiting for input is still
  by design. A host that switched sources by guessing would make the same template match and
  stop matching for no reason anyone could hear.

**Who decides for a VM:** the module's own `[screen]` if it has one; otherwise the nearest
dependency that declares one — smallest depth first, then the earliest in manifest order
(`dependencies` before `optional_dependencies`) — counting only dependencies that are
themselves `code_module`s **and** require `screen` or `ocr`; otherwise `standard`. So a runtime
that every game module is built on declares it once, and a single module can still override
it. Resolved each time the VM is built, from the manifests as they are on disk then: reloading a
module after editing its table applies it, and reloading a runtime after editing ITS table
applies it to every module that depends on the runtime through `dependencies`, directly or
not, because those are rebuilt with it. A module that reaches the runtime only through
`optional_dependencies` is not rebuilt with it; reload that module itself. Unknown values are named in the log and read as
`standard` (for `capture`) or the standard fallback (for `fallback`); the module still loads.
Hosts that predate the table ignore it.

On macOS the table is accepted and ignored. A switch in the Application settings tab ("Let
modules that ask for it read the screen through the graphics card", on by default) turns
duplication off for every module on a Windows machine where it misbehaves.

## More than one file

The entry file pulls in the module's other files with [`host.include`](api/include.md), which
runs a file of the same module once per VM and returns what it returns.

Luau's own `require` does not work in module code: every file is loaded under a name that
`require` does not accept, so `require("./lib/coords")` raises `require is not supported in
this context`.

## Paths and files

- **Relative paths resolve against the module whose code makes the call** — for a
  `code_module` that is its own folder even while its code runs in a dependent's VM. See
  [Paths](api/index.md#paths).
- **Image paths handed to the overlay runtime must be absolute** — `host.path("images/…")` —
  and it refuses a relative one when the overlay binds, because the search is made by the
  runtime's code, which would look in its own folder.
- **Reading is text only.** [`host.resource.read`](api/resource.md#host-resource-read) returns
  a file as a UTF-8 string and raises on anything else; `host.resource.exists` asks whether one
  is there. Nothing reads a file as bytes. Binary data such as template pixels ships as JSON
  numbers or a Luau table.
- **There is no write API** beyond the PNG screenshots of
  [`host.screen.save`](api/screen.md#host-screen-save). Values that must survive a restart go
  into [`host.settings`](api/settings.md) — booleans, numbers and strings.
- **Nothing confines a path to the module.** `host.path`, `host.resource`, `host.sound.play`
  and the image-search paths join a path onto the module's folder as written: `..` is not
  refused and an absolute path is used as it stands. Only `host.include` checks that a path
  stays inside the module, and on macOS that check misses `..` (see its page).

## What the format does not protect

A module is arbitrary Luau code running inside the application, and a module package is an
unsigned folder. The capability list is enforced per namespace, which catches a module
reaching for something by accident; it is the author's own statement, not a sandbox. There is
no signature, no trust store, and no confinement of file access to the module's folder.

## Proposed in the first draft and not built

The draft of 2026-06-21 described the following. None of it exists; a module written against
it loads — unknown keys are ignored — and then does not behave as the draft said.

- **A module as a ZIP package**, unpacked into a content-addressed cache when it is installed.
  Installing and starting use plain folders; only a `.zip` given on the command line is
  unpacked, into a temporary cache.
- **Native libraries**: the `native/` folder, the `[native]` table, the `"ffi.native"`
  capability and a `host.ffi` namespace. Nothing in the host loads a library for a module.
- **`engine_api` checked at load.** It is read and ignored.
- **A package-scoped `require`** (`require("@self/overlays/serum2")`) with `..` rejected. Use
  `host.include`.
- **`host.read(rel) -> string | buffer`** for byte reads. There is `host.resource.read`, text
  only.
- **Logical paths resolved by every capability** —
  `overlay:addGraphicalButton{ image = "assets/…" }` finding the file in the module that wrote
  it. The overlay runtime requires absolute paths instead.
- **Resource access confined to the package, and signed packages** with an Ed25519 trust
  store.
